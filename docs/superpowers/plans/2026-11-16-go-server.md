# Go Server Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the dashboard server (PHP 8.3 behind Nginx + PHP-FPM, plus the watchdog script) with one Go program `fw-alarm` that answers the same addresses with the same answers on the same data folder — proven by the existing black-box tests — and switch the Oracle VM over with PHP kept as a seconds-away fallback for 14 days.

**Architecture:** One Go module at the repo root, one binary with the subcommands `serve`, `watchdog`, `check-config`, `version`. The watchdog stays a separate process started by the existing systemd timer; server and watchdog share the data folder through the same `flock` lock files PHP uses today. The frontend under `nas_dashboard/assets/` is embedded unchanged. On the VM only two things flip at cutover: which upstream Nginx forwards to and what the timer starts.

**Tech Stack:** Go (current stable at execution time, ≥ 1.23, pinned in `go.mod`), standard library + `golang.org/x/crypto/bcrypt` (vendored), `CGO_ENABLED=0`, builds for `windows/amd64` (local tests) and `linux/arm64` (VM). Tests: Node 24 `node --test`, headless Chrome over CDP for the browser scenarios, PHP 8.3 only as the reference implementation until Task 24.

**Spec:** `docs/superpowers/specs/2026-11-16-go-server-design.md` (German; § numbers below refer to it). Read it and `CLAUDE.md` before any task — `CLAUDE.md` is the list of rules that must survive, the tests are how they are checked.

## Global Constraints

- **No accidental alarm (spec §14):** on the PC and in staging `bark_host` always points at a mock on `127.0.0.1`; on the live system never trigger "Alarm an alle", Entwarnung, Demo-Alarm or `keys_test` except the one joint demo alarm in Task 23. Live checks use only status pushes, the TEST command, HEAD/preview mute calls, the user's OWN mute link and a watchdog run.
- Never touch `boss925_alarm_bark/`, `platformio.ini`, `nas_bridge/`, `cloud_watcher/`.
- Addresses keep their `.php` endings forever: `/`, `/index.php`, `/dashboard_api.php`, `/api/{status,poll,ack,keys,mute,alive,health}.php`, `/manifest.json`, `/assets/…`. A wrong machine token is answered with status 403 and the body exactly `FORBIDDEN`.
- Answers to the box (`status`, `poll`, `ack`, `keys`) never wait for Bark; anything sent to Bark from those requests runs after the response.
- Test files under `tests/backend/` and `tests/dashboard/` are the contract: they are not edited to make Go pass. The only allowed edits are the ones a task names.
- Data folder: same file names (`<name>.php`), same guard line `<?php http_response_code(404); exit; ?>`, same fields. Read as leniently as PHP (`phpval`), write canonical JSON, keep fields the code does not know, never rely on the key order of a JSON object.
- All texts (API messages, Bark texts in ASCII, HTML pages) are copied verbatim from the PHP source. Texts naming PHP or Nginx change only in Task 24.
- Go code: identifiers in English, comments in German with real umlauts (project convention). Every function that ports a PHP function carries a comment line `// PHP: <php_function_name>`.
- Dependencies: standard library and `golang.org/x/crypto` only, vendored (`go mod vendor`, builds use `-mod=vendor`). No CGO. The server must run on Windows (local tests) and Linux.
- Lock order as in PHP: `keys`→`log`, `command`→`log`, `watchdog`→`log`; `settings` and `notify` alone; `log` always innermost. `keys.ExpireStaleMutes`, `keys.EnsureMuteTokens`, `keys.RepairBrokenDemo` take `keys` themselves — never call them while holding it. No Bark request while holding any lock.
- Bark client: connect 5 s, total 10 s, no redirects, response body discarded, HTTP 4xx never retried, 500 ms between rounds.
- The repo is public: no real host names or addresses in tracked files. Copies of live data or config live only in a folder with mode 0700 outside the repo and outside any cloud folder, and are deleted after use.
- On the VM nothing root executes and nothing secret passes through `/tmp`; use a folder in the home directory (mode 0700). Oracle stays Always Free.
- Line endings: `*.go`, `go.mod`, `go.sum`, `tools/*.sh`, everything under `server/` are LF (`.gitattributes`).
- Commits directly on `main`, German messages with umlauts, ending with the `Co-Authored-By:`/`Claude-Session:` lines from the session reminder. Push before every deploy.
- Verification commands: `go vet ./... && go test ./...`; `node --test "tests/backend/*.test.mjs"` (PHP); `bash tools/test-go.sh` (same tests against Go); `node --test "tests/dashboard/*.test.mjs"`; browser scenarios `node tests/dashboard/e2e/run.mjs <name>`.
- **Quality and security bar** (user, 2026-11-17: best practices throughout, robust, security first). Every Go task also passes `gofmt -l cmd internal nas_dashboard` (prints nothing), `staticcheck ./...` and `govulncheck ./...` — development tools installed with `go install`, never module dependencies. Secrets (machine and watcher token, Bark keys, mute tokens, passwords, session ids, CSRF tokens) are compared in constant time, come from `crypto/rand` when the server generates them, and never appear in a log line, an error text, a redirect or any URL the server builds. Every request has a size limit and a time limit. No file path is built from request input. HTML only through `html/template`. No error is dropped without a comment saying why. Everything that parses outside input (`phpval.Decode`, `web.Form`, the config loader, log lines, the mute link's query) gets a Go fuzz test: its seed corpus runs in every `go test`, and `go test -fuzz` runs for 30 s once in the task that creates it.
- Spacing: at least 3 quiet days between flashing the box and Task 22; Task 24 not before 14 quiet days after Task 22; passkeys only after Task 24.

## Review Focus

1. **Two requests at the same moment** (PHP's test server handled one at a time, so no test ever exercised this): 20 parallel polls with one pending command → exactly one answer carries it; 30 parallel wrong logins with `login_max_failures` 8 → at most 8 password checks, the rest 429; 10 parallel `keys_add` → 10 entries with distinct ids and the version raised by exactly 10. Test: Task 16 `tests/backend/concurrency.test.mjs`.
2. **Files PHP wrote over months in shapes a Go decoder rejects:** `[]` where an object is meant, flags stored as `true`/`1`/`"1"`, numbers as strings, list entries that are not objects, extra fields nobody remembers. Expected: read like PHP, keep unknown fields on rewrite. Test: Task 5 `TestLenientShapes`, Task 10 `TestMutateKeepsUnknownFields`, Task 18 parity run on a copy of the live data.
3. **The connection drops or the service restarts in the middle of "Alarm an alle"** (Cloudflare cuts after 100 s, a phone loses signal, a deploy lands): every recipient still gets the alarm and `nas_alarm` is written to the log. Test: Task 14 `TestBroadcastSurvivesClientDisconnect`, Task 16 `TestShutdownWaitsForBroadcast`.
4. **A typo in `config.json` on the live server:** the server keeps the last good configuration, `check-config` names the problem without printing secrets, the watchdog prints `KONFIGURATION FEHLERHAFT` and exits 1 — nobody is locked out and no alarm path stops. A deliberately changed password still logs that account's sessions out at once. Test: Task 6 `TestProviderKeepsLastGood`, Task 1 `session.test.mjs` case "Passwortwechsel".
5. **Daylight-saving switches and a VM without time-zone data:** `[d.m.Y H:i]` stamps, quiet hours across midnight, the weekly report's weekday/hour must follow Europe/Berlin exactly. Test: Task 9 `TestStampBerlinSummerWinter`, `TestQuietHoursAcrossMidnightAndDST`.
